# MacTower: три режима сна

Статус: спецификация для согласования; реализация ещё не начата.

## Согласованное поведение

Пользователь выбирает один постоянный режим без таймеров. По умолчанию действует
«Обычный», выбранный режим сохраняется между перезапусками. Настройки питания
macOS не переписываются.

| Режим | Компьютер | Экраны |
| --- | --- | --- |
| Обычный | Автоматический сон по настройкам macOS | Автоматическое отключение по настройкам macOS |
| Mac не спит | Автоматический сон запрещён MacTower | Могут гаснуть по настройкам macOS |
| Mac и экраны не спят | Автоматический сон запрещён MacTower | Автоматическое отключение запрещено MacTower |

«Обычный» означает отсутствие запретов **со стороны MacTower**. Другие приложения
могут продолжать удерживать компьютер или экраны включёнными.

Ручной сон, закрытие крышки и защитный сон при разряде не обходятся. Блокировка
сеанса не снимается. Режим не отменяет заставку, не будит уже погасший экран и не
включает отключённый монитор. После обычного пробуждения ограничения продолжают
действовать. Работа в Dark Wake не гарантируется этими API.

## Предлагаемые границы первого этапа

- Управление из локального меню приложения и настроек.
- Один root LaunchDaemon владеет запретом сна: закрытие GUI и logout сами по себе
  не отменяют выбранный режим. Это соответствует фоновой работе башни.
- Режим действует и при питании от батареи; интерфейс предупреждает о расходе
  энергии, особенно при включённых экранах.
- Новые HTTP/MQTT-команды, расписания, таймеры и автоматический выбор режима по
  источнику питания не входят в этап. HTTP остаётся только для чтения.
- Уведомления по AI — отдельный следующий модуль: пользователь выбрал идею,
  но канал доставки (macOS, Home Assistant или оба) ещё не согласован.

## Интерфейс

В General появляется секция Sleep с переключателем из трёх положений. В меню
MacTower — подменю Sleep mode с теми же пунктами и отметкой выбранного режима.
Обе поверхности используют один источник состояния, без отдельных UserDefaults
для копий этой настройки. Названия в коде и UI следуют текущему английскому
интерфейсу проекта: Normal, Keep Mac awake, Keep Mac and displays awake.

Показываются сохранённый режим, состояние применения и понятная ошибка при
неудаче. «Применено» означает, что macOS приняла необходимые assertions, а не
гарантию физически включённого экрана или отсутствия вынужденного сна.

Пока ответ сервиса не получен, состояние неизвестно, а не «Обычный». При недоступном
сервисе переключатель отключён; указано, что требуется установленный сервис.
Устаревший статус не выдаётся за актуальный. При незавершённой операции изменение
режима временно недоступно. Отображение обновляется при открытии меню/настроек,
возврате в приложение и после ответа на изменение.

## Архитектура

Существующие точки расширения: `ManagementOperation` и DTO в `MacTowerCore`,
аутентифицированный `DaemonXPCServer`, `DaemonClient`, `AppServices`,
`MenuBarView`, `SettingsView` и жизненный цикл `MacTowerDaemon`.

Добавляется небольшой изолированный контроллер питания с внедряемым backend для
проверок. Модель содержит конечное перечисление трёх режимов, выбранный и
сохранённый режимы (они могут различаться при ошибке записи), текущее подтверждённое
состояние assertions и классифицированную ошибку.
Нативные IOKit-вызовы отделены от хранения и интерфейса. Новые внешние зависимости
не нужны; весь код остаётся в `src`, тесты — в `tests`.

Управление проходит по существующему XPC с проверкой UID владельца установки и
подписей приложения/сервиса. Новые конечные операции читают состояние и меняют
только режим; неизвестные значения и чрезмерные payload отклоняются. Произвольных
команд, путей и аргументов внешних программ нет. Новый UI-запрос имеет конечный
тайм-аут и exactly-once завершение при ответе, разрыве или отмене; можно использовать
существующий `XPCReplyLedger`. После неоднозначного тайм-аута сначала читается
актуальный статус, запись автоматически не повторяется.

Настройка хранится отдельно от AI/сетевой конфигурации в `power-control.json`
в root-хранилище MacTower через существующий `PrivateFileStore`: приватные права,
атомарная замена и отказ от небезопасных ссылок. Сохранение других настроек не
может перезаписать режим сна. Отсутствующий файл означает Normal. Повреждённый
или неподдерживаемый файл не перезаписывается молча: питание работает без
assertions, ошибка видна в UI, сбор AI-данных продолжает работать.

## Нативное управление и ошибки

Используются только публичные IOKit assertions:

- Normal: нет принадлежащих MacTower assertions.
- Keep Mac awake: `kIOPMAssertPreventUserIdleSystemSleep`.
- Keep Mac and displays awake: `kIOPMAssertPreventUserIdleDisplaySleep`; этот тип
  сам препятствует также автоматическому сну системы.

Создание через `IOPMAssertionCreateWithName` без тайм-аута, освобождение через
`IOPMAssertionRelease`. Причины имеют фиксированные имена MacTower, без названий
аккаунтов, окон, путей и пользовательского содержимого. `pmset`, `caffeinate`,
эмуляция ввода и API пробуждения экрана не применяются.

Переходы сериализованы. При включении запрета сначала сохраняется выбранный режим;
при ошибке записи текущие режим и assertions не меняются. Затем контроллер
приводит assertions к сохранённому режиму. При переходе между двумя режимами
запрета новый assertion
создаётся до освобождения старого. Повтор уже применённого режима не создаёт
дубликатов. При ошибке создания сохраняется прежний assertion; ошибка применения
и различие желаемого/текущего состояния видны пользователю.

Normal — отдельный путь: освобождение всех собственных assertions выполняется
даже при ошибке сохранения. В этом случае UI явно сообщает, что Normal не сохранён
и прежний режим может восстановиться после перезапуска. Применение в текущем
процессе подтверждается отдельно; простое чтение статуса не включает старый режим
обратно. Сохранение повторяется только явно.

Неудачное освобождение не считается успехом: ID остаётся учтённым для последующей
очистки. При частично завершённом переходе показывается ошибка, а не фиктивный
успех. Следующая явная попытка согласует учтённые assertions с выбранным режимом,
не накапливая новые. Фоновый бесконечный цикл повторных записей не нужен.

При старте сервиса применяется сохранённое желание. Ошибка IOKit не останавливает
AI-сенсоры и сетевые публикации. При штатной остановке освобождаются все собственные
assertions до потенциально долгого сетевого завершения; сохранённый режим не
сбрасывается. После принудительного завершения
освобождение ресурсов процесса и повторный старт launchd проверяются отдельно.

## Установка и проверка

Никаких изменений в живой системе при сборке и автоматических тестах. Для нового
подписанного XPC-контракта установленную пару GUI/daemon нужно обновить обычным
`make install`; запуск этой команды — отдельное явное действие пользователя.
Dev-бандл без установленного совместимого сервиса не получает второй, локальный
владелец assertions. `make uninstall` останавливает сервис и освобождает его
ограничения, но сохраняет режим вместе с прочими данными; повторная установка
восстановит его. `make purge-data` по-прежнему отдельно очищает данные.

Автоматическая приёмка с поддельным backend, без влияния на сон рабочего Mac:

- Все три значения и отказ от неизвестного режима; старое отсутствие настройки.
- Матрица всех переходов, повтор одинакового выбора и отсутствие утечек ID.
- Ошибки create/release/хранилища, частичный переход и повторное согласование.
- Восстановление после старта, штатный stop, отсутствие дубликатов при конкуренции.
- XPC-разрыв, поздний ответ и тайм-аут без ложного подтверждения или повторной записи.
- UI показывает неизвестное/сохранённое/применённое состояние раздельно.
- Режим не попадает в новые управляющие LAN-маршруты и не ломает старые DTO/тесты.
- `make check`; README, SECURITY и architecture обновляются вместе с реализацией.

Ручная приёмка установленной сборки проводится отдельно и с согласия пользователя:
проверить assertions только процесса MacTower, реальное гашение экрана и простой,
возврат в Normal, питание от сети/батареи, ручной сон/пробуждение, блокировку и
logout, остановку/аварийное завершение/перезапуск сервиса и обновление подписей.
Полный разряд батареи ради проверки не требуется. Тестовые backend не заменяют
эти наблюдения; чужие assertions не снимаются.
